# amb 与 Racket sequence-generate* 的统一流协议实验

2026-11-14；Racket 9.3 CS；基线 `d7edfd5e8b3bcbc5dcd04cf810fff7fed02c609c`。

结论：**这条路线值得继续作为下一版研究基础。它确实消除了原生 sequence 到 amb 的逐元素节点转换，四种调度可以保留，结合结构也可以继续融合；它不是普遍更快的内核。** 修正观察器整数计数并重测全部负载后，本机 C 多数搜索/人工流负载约慢 6%–40%，大量失败分支约慢 57%；D 的最高中位数开销约 46%。C 的原生 sequence 直接消费约快 9%，完整往返约慢 6%。结果支持继续研究互操作，但不支持“values 替换 cons 就会更快”。

建议先以 C 的单暂停生产为基础，明确惰性创建这一 API 决策，保留 eager 迁移入口；D 的计数及安全融合继续独立研究。原始研究内核与 pkgs/ 没有修改，本独立实验整理到新分支供审阅，入口见 REVIEW.md。本文为可运行研究原型的结论，不是正式包升级说明。

后续决策：Noah 已确认，为取得本任务的互操作性与 API 收益，50% 以内的性能开销可以接受。多数所测 CPU 中位数在这个范围内，但 C 的失败密集项在发布重测中超过该参考范围，须单独审阅；D 本轮所测中位数均在范围内。这不构成任意负载的时间上界，也不代表内存分配限制为 50%。

文中用三类证据：**实测**指本次实际运行；**源码推导**指按实现和官方约定分析；**待验证**指尚未运行或未证明的推测。

## 1. 当前代码状态与四个实验版本

初始工作区为空，指定分支检出后干净，没有发现 AGENTS.md。阅读对象包括 kernel、model、catenable、README 的机制/结合律/强制时机/代价/API 讨论，以及相关测试与现有 benchmark。baseline 保存原版文件，不改写其算法或测试期望。

| 版本 | Stream | merge 参数 | 创建搜索时 | 用途 |
|---|---|---|---|---|
| A | 空表 / 答案 pair / 暂停 thunk | 已求值 Stream × 生产 Stream 的 thunk | 执行到首事件 | 原版基线 |
| B | 与 A 相同 | 两个生产旧 Stream 的 thunk | 与 A 相同，merge 立即请求左边 | 分离接口对称化的影响 |
| C | thunk → 两值 result,next | Stream × Stream | 首次推进才执行 | 统一协议，仅生产/接受暂停 1 |
| D | 与 C 相同，允许正整数暂停块 | Stream × Stream | 与 C 相同 | 计数解码及保守的块融合 |

B 的 thunk 仍生产旧三分支数据类型，**不是 C 的统一 Stream**。B 保留旧的可调用调度记录，通过适配 ready merge 的薄层实现；它足以测量该过渡实现的开销，不能解释成所有双 thunk 实现的成本下界。改动见 B.diff。

C/D 的搜索边界与捕获的续延直接返回两个值：

```racket
(define (amb-reify thk)
  (λ () (reset-at tag (values (call-with-values thk list) done))))

(define (amb-fail) (shift-at tag k (done)))
(define (amb-pause)
  (shift-at tag k (values 1 (λ () (k (void))))))
```

`unit` 闭包仍作为构造单答案流的便利函数存在，但正常返回路径没有先建立 unit 再立刻调用。选择分支在其 turn 到达时调用续延，续延也直接交付两个值。公开可传递的 Stream 和持久的尾状态仍然需要过程或可调用记录。

## 2. 与 Racket 原生协议的精确关系

官方依据：[Sequences / sequence-generate*](https://docs.racket-lang.org/reference/sequences.html)。另核对安装的 Racket 9.3 `collects/racket/private/for.rkt` 的 `sequence-generate*`，以及 `share/pkgs/racket-doc/scribblings/reference/sequences.scrbl`。

**官方约定与本次实测一致：**

| 情形 | result | 消费规则 |
|---|---|---|
| 单返回值 x | `(list x)` | 答案，随后才能调用 next |
| 多返回值 x,y | `(list x y)` | 一整个答案，不能拆成两个答案 |
| 零返回值 | `'()` | 仍然是答案，不能当终止 |
| 序列结束 | `#f` | 忽略 next，不再调用 |
| amb 暂停 | 正整数 | 原生 sequence 不产生；amb 额外解释 |

`sequence-generate*` 的调用会初始化 sequence 并取得第一个元素；返回的 next 才继续第二个元素。源 sequence 的 `pre-pos-next` 等操作还可能在元素提取时执行，所以不能假定“调用仅建立对象，不读取数据”。终止时 next 是会抛 `exn:fail:contract` 的过程，不要求它返回一个可反复读取的空流。

因此，下式确实可直接作为 C/D 的 Stream，也能直接作为其 merge 参数：

```racket
(λ () (sequence-generate* (in-naturals)))
```

这里的一次初始 λ 是必要的惰性入口；**无需为每个元素另外造 amb cons 节点或适配闭包**。后续过程就是 Racket 返回的 next，按原样继续传递。但这不意味着所有分配消失：原生实现自己为整组值建立列表和后继过程，merge 还会建立自己的调度状态。

测试通过的来源：`in-naturals`、`in-range 100`、`in-list '(a b c)`、`in-parallel` 的多值元素、自定义零值 sequence、port 的 single-pass sequence；与 reify 流合并、再反射和 sequence 输出也覆盖。

**单遍的含义要写清楚。** Racket 并不强制每个 next 只能调用一次。对于无状态的序列，重复同一 next 可能重算同一位置；对于 port 等源，重复调用可能继续消费共享状态。重复初始 λ 对 naturals 会重新从 0 开始，而不是前进到下一个数。amb 的调度残余必须采用一次消费/一次转移的所有权约定；这比“不缓存”更具体，融合时读字段并接管残余也算消费。

## 3. 事件等价与执行时机是两个问题

四种策略在相同参数作用域内消费时，通过了相同 fuel 下的事件与逐事件副作用对照。**这不等于创建对象时的行为完全兼容。**

最小反例：

```racket
(define n 0)
(define s (amb-reify (λ () (set! n 1) 'x)))
n
;; A/B: 1；C/D: 0。C/D 第一次推进 s 后才变成 1。
```

参数的作用域也因此发生可见变化：

```racket
(define p (make-parameter 'outside))
(define s
  (parameterize ([p 'creation])
    (amb-reify (λ () (p)))))
;; 在 [p 'consumption] 中消费：A/B 首答案 creation，C/D consumption。
```

旧版的后续事件本来就会受到消费时参数作用域影响；C/D 把这个边界扩展到了首事件。把 parameterize 写进搜索 thunk 内可以让它成为所捕获的计算的一部分。实验没有自动冻结全部动态参数，因为那又会引入另一种语义。

`amb-reify/eager` 提供旧式首段执行：先推进一次，再把首个 result,next 包成一个 Stream。它多一个边界闭包，但不需要逐元素转换。它只兼容搜索入口的首段时机，不能使直接的 C/D merge 构造调用自动变回旧式 eager 调用。

副作用、续延与惰性边界的判断：

- **实测：** 随机有限搜索中，每个交付事件时的 tag 副作用轨迹一致；局部搜索、once、ifte 和混合策略通过；一次暂停前后的 dynamic-wind 进入/退出顺序在消费后相同。
- **源码推导：** 右分支不会在调度轮到它之前推进；恢复续延是取得下一事件的计算，不能再误标成额外暂停。捕获边界仍是最近的 amb prompt。
- **待验证：** 异常处理器、任意用户自定义 continuation marks、多 prompt 混合、重入消费以及复杂 dynamic-wind 程序没有完整建模或穷举。不能把一项 dynamic-wind 测试外推为全部控制行为等价。

完全惰性的 raw Stream 对原生互操作很自然；是否让现有公开 amb-reify 同时改变创建时机，是需要明确记录的版本迁移决策，不能当成内部优化悄悄合入。

## 4. 暂停计数的正确解释

`n` 表示事件词 `P^n`，不是“调度器自动跳过 n 次换边”。D 的处理如下：

| 策略 | 遇到 n 个暂停时 |
|---|---|
| append | 可以原样交付 n；该侧保持 turn |
| interleave | 交付 1，再把对侧与当前剩余 n−1 暂停交换 |
| alternate | 暂停同上；答案后也交换 |
| level | 本轮每支只消耗一个暂停；轮末统一交付一次暂停 |

例如 `level(P^5 a, P^3 b)` 展开为 `P P P b P P a`；D 可先返回压缩的 3，但前 1、2、3 个逻辑事件依然各为暂停，不能提前执行 b 或 a。

D 另允许一个严格受限的优化：本轮结束后，所有等待者都已经是已知、纯粹的 `paused(n,next)` 记录时，取剩余计数的最小值，一次表示共同的若干空轮；不调用任何 next 来探测。任何普通 thunk 都是融合屏障。计数扣减后保留原顺序。这里没有把连续的用户 `amb-pause` 偷偷合并，因为两次暂停之间可能有副作用或策略观察。

**实测：** 1..8 的暂停块两两组合 × 四策略 × 七种 fuel，与单暂停展开一致；另有 1,800 个嵌套混合策略表达式 × 四种 fuel，C 的展开与 D 的压缩一致；十亿暂停块只取前四事件也会立即返回。opaque 尾部不会为寻找下一块而提前调用。

以上是系统化测试和按纯记录展开的推导，尚无机器检查的普遍等价证明。第一版只生产 1 是稳妥的实现范围；正整数协议的接收与压缩生产可以分开推进。

## 5. appended、leveled 的融合保留下来了

旧表示的 callable record 有时本身就是已经可见的暂停，新表示的 callable record 只是下一事件的计算。不能只把旧代码里的 cons 替换成 values。

C/D 中：

- `appended(s,ts)`：推进 s，之后依次是 ts。当前请求对象又是 appended 时，读其字段，把内层 ts 接在外层 ts 前面。遇到答案或暂停直接返回 result 和残余记录，结束后才请求下一个待办。
- `leveled(ws,s,ts)`：ws 已在本轮暂停，s 正在推进，ts 尚未推进。碰到嵌套 leveled 时，分别按 `ws ++ inner-ws`、`inner-ts ++ ts` 合并。本轮待办耗尽才显式返回暂停；下一轮的计算留在 next 中。

两者仍使用原始 catenable 列表，拼接不复制整个列表。内层记录的展开不能执行源流。融合对外延结合律之外，还依赖单遍所有权与保持源调用时机。

**实测规模对照：** 在“取一个答案，合并一个空分支，再对残余重复”的程序中：

| n | C append 的 cat steps | C level 的 cat steps | 未融合 append 的 merge 调用 |
|---:|---:|---:|---:|
| 2,000 | 7,994 | 7,994 | 2,005,000 |
| 4,000 | 15,994 | 15,994 | 8,010,000 |
| 8,000 | 31,994 | 31,994 | 未运行 |
| 16,000 | 63,994 | 63,994 | 未运行 |
| 32,000 | 127,994 | 127,994 | 未运行 |

这些列计数的操作种类不同，不能把比值直接当时间加速比；增长趋势明确。32,000 的两种融合程序均为约 6 ms 的单次观察；未融合 append 的 4,000 为约 62 ms。这里只把计步用于规模验证，单次时间不当作正式七次中位数 benchmark。细节在 fusion-scaling.json。

源码推导：融合形状没有因 Values 协议而丢失，原有基于残余状态单次消费的摊销分析有望迁移。本文没有完成包含 D 块压缩分支的新复杂度证明，也不把 interleave/alternate 的嵌套成本称为不可避免的下界。

## 7. 可复现性能测量

机器暴露为 x86_64 Linux / AMD EPYC 9V74；Racket 9.3 CS。环境无法读取完整 sysfs CPU 数量与 quota，未设置 CPU 亲和或固定频率，不能声称独占稳定机器。环境与安装器 SHA256 已记录。

每个版本/负载独立进程，单进程 20 秒硬超时；一个预热加三次有界 CPU 校准，按中位数选取约 100 ms 的测量批次（最多 400 次工作调用），七次批次，每次前完整 GC。所有重复验证答案数、逻辑暂停数和 checksum；四版结果也逐负载核对。版本顺序分组轮换；测试不并发。

分配量是 `current-memory-use 'cumulative` 的增量，表示估计的累计分配，**不是存活堆大小或峰值**。CPU/real/GC 来自 time-apply，ms 计数有分辨率限制。每个 JSON 保留七次原样数据；CSV 给出所有指标的中位数、min/max、对 A 的比值以及每答案/暂停平均成本。min/max 不是置信区间。

发布前发现原 drain 的 `(min +inf.0 r)` 会将暂停计数浮点化，改为选择原操作数，且重新测量全部 13×4 负载。run-bench.py 现在检查计数必须保持整数。最初下载包的旧数字不应与本发布表混用，细节见 results/BENCHMARK-NOTES.md。

## 8. pair、values、closure 与 GC 的成本

micro-producer 通过运行时符号 dynamic-require 取得，避免调用方简单内联后消掉构造与解构。每项 2,000,000 次，预热后七次测量；pair/values/closure 消费两个动态字段并累计校验值。thunk 为单捕获字段再调用；reused-thunk 为固定、不再分配的两值过程，作为调用/接收的控制项，校验值不同，不能和前几项作严格的单指令差值分解。

| 操作（2,000,000 次） | CPU ms [min,max] | Real ms | GC ms | 总分配 MiB | 字节/次 |
|---|---:|---:|---:|---:|---:|
| pair | 8 [7,9] | 8 | 0 | 30.537 | 16.010 |
| values | 7 [6,7] | 7 | 0 | 0.016 | 0.008 |
| closure | 11 [10,12] | 11 | 0 | 61.058 | 32.012 |
| thunk | 11 [10,14] | 11 | 0 | 30.537 | 16.010 |
| reused-thunk | 7 [6,8] | 7 | 0 | 0.016 | 0.008 |

**本机实测：** pair 约 16 字节/次；捕获两个字段的两值 closure 约 32 字节/次；捕获一个字段的 thunk 约 16 字节/次。直接 values 路径和重用 thunk 的路径分配近零；表中小额是测量/循环相关开销，不能解释为每次 values 固定分配 0.008 字节。

因此，将 `(cons vs done)` 改成 `(λ () (values vs done))` 确实可能只是把 pair 换成 closure；闭包大小取决于捕获字段，done 是全局绑定时未必需要捕获它，不能把这次双字段 closure 的 32 字节直接套到所有 unit 上。多值返回本身不建立一个必须长期保存的 cons 节点，本次固定两值直接调用也没有可见的逐次节点分配；但生产者、接收点、跨 continuation 路径和编译器优化都会影响整体分配。

`let-values` 的接收、参数传递、间接过程调用、分支判别都要执行。micro 的 values 与 reused-thunk 时间接近，只说明这个简单路径的额外开销有限，不能据此把 thunk 调用视作免费。构造再调用 closure 的时间包含分配和调用两项，不能从总差值精确分出各自纳秒数。

GC 的零记录是 ms 分辨率下的零，不是证明无 GC 工作。正式搜索 benchmark 中，大量失败和宽选择都有可测 GC；但 C 在某些场景的更多 CPU 不能全归因于 GC。源代码可指出更多左生产者闭包、调度记录和多值交付边界，**具体热点占比仍需 profiler**。本实验没有测量寄存器级多值传递或每个编译器生成的 closure 布局。

## 9. 公开 API 建议

| 面向用户的接口 | 建议 |
|---|---|
| `in-amb` | 保留，普通直接风格入口；明确创建时机 |
| `in-answers` | 保留，接受 raw amb Stream，跳过暂停，按原返回值个数生成 sequence 元素 |
| `sequence->amb-stream` | 提供一次初始 λ 的便利封装，不复制每个元素 |
| `amb-reify` / `amb-reflect` | 作为高级互操作与局部搜索接口；明确 raw Stream 的单遍所有权 |
| `amb-reify/eager` | 若默认入口改为惰性，作为迁移选择；也可反过来让旧名称保持 eager，另命名惰性入口 |
| `amb-await` | 改成返回两个值 (result,next)，result 为列表或 #f；旧匹配 cons 的调用方必须迁移 |
| `in-amb-events` | 新增惰性完整事件 sequence；答案为整组值列表，暂停为单独的 pause 符号，计数自动展开 |
| `amb-events` | 保留有限 fuel 的调试收集接口；目前原型保持旧的单值显示，零/多值用 in-amb-events |
| `amb-pause` | 普通程序员只用这个操作，不直接处理计数 |
| 暂停块构造与底层协议 | 放高级接口或子模块，协议文字可公开；不要要求每个使用者操作裸整数 |

raw Stream 与 Racket 的 `stream?`、带缓存的 racket/stream 对象不是同一类型，不建议把任何 procedure? 都称为可验证的 amb-stream?。轻量边界 contract 可以检查返回值形状，但每步完整检查有开销，是否需要应另测。prototype 的 all-defined-out 方便实验，不是建议最终导出 done、cat 调度记录等内部符号。

`in-answers` 与 `in-amb-events` 的 sequence 对象在本原型中禁止重复初始化，避免误共享一次性搜索；底层 thunk 没有统一包上重复消费检测。需要缓存/重放时应显式转换，不隐式给所有流 memoize。永远暂停的流在“只取答案”接口上仍可永远等待，这是该观察方式的性质；需诊断进度时用完整事件与有限 fuel。

完整事件用列表包装答案，故 `(values)` 是 `'()`，`(values #f)` 是 `'(#f)`，`(values 'pause)` 是 `'(pause)`，都不和单独的暂停事件混淆。底层自然数计数无需暴露给普通 for 用户。

## 10. 采用建议与剩余工作

**已实测可行：** 原生 sequence 入口无需逐元素适配；零/多返回值不丢失；四种调度及局部组合在本测试范围内保持语义；结合融合没有退回匿名闭包链；D 的已知纯暂停块可以安全地按逻辑事件展开。

**根据源码与测量作出的判断：** 统一协议更适合作为与 Racket sequence 互操作的高级边界。双 thunk 本身不是主要成本来源，直接产生两个值也确实可减少中间 unit 包装；但 all-thunk 形状、调度状态、分支闭包与消费方式共同决定整体代价。接口一致性和较低转换成本是真实收益，速度需要逐负载判断。

建议继续采用 C 作为设计主线，D 保留为可选实验：普通 amb-pause 先只生产 1；不要为了压缩计数改变策略方程。若后续公开承诺全部正整数，消费者应采用 D 的逐次解码规则，再独立决定是否打开已知纯块的融合。

正式替换前应完成：明确现有入口 eager/lazy 的迁移方案；迁移所有匹配旧构造子的消费者与 n 路策略；检查 Typed Racket 与 contract；在用户目标机器上复测失败密集的真实 Kanren 负载，并用 profiler 分清闭包/调度/控制转移热点。本次没有完成这些，不能称为可直接发版的包。

如果要求所有旧搜索性能下降不超过 5%，本轮结果不满足。Noah 已接受 50% 以内的成本作为考虑范围；D 本轮所测中位数符合，C 的失败密集项约 57% 应单独分析，不能宣称所有候选均符合。整体证据足以支持继续统一协议；应在真实负载与目标机器上定位这项开销，再决定最终实现。
