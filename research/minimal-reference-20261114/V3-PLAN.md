# 正式版设计决定与模块边界（供审核）

本稿记录 Noah 在 demo `2613c43` 之后确认的正式版方向。它是实现前的规格与审阅入口；当前 demo 尚未按这些模块拆分，也没有据此修改 v2 正式包。前面的 DESIGN.md 是较早参考模型的设计，涉及强制代数律、初始化策略等内容时，以本稿的新决定为准。

## 1. 公开模块

| 模块 | 主要导出 | 职责 |
|---|---|---|
| amb/base | make-amb、amb-fail、amb-pause、current-amb-merger；in-amb、in-amb/do 等搜索观察入口 | 最核心的选择效应、策略参数与搜索边界 |
| amb/main | 重导出 amb/base；增加 amb、for/amb、for*/amb | 构造备选的便利语法与向量、循环供应机制 |
| amb/merge | amb-append、amb-interleave、amb-alternate、amb-level | 独立的原生生成过程合并函数 |

`require amb` 继续作为常用入口，对应 amb/main。ambKanren 等使用方可只依赖 amb/base，并选用 amb/merge 或自行定义合并过程。

建议四种标准 merge 统一从 amb/merge 导出；base 内部使用同一个 amb-append 作为默认值，不必因此重导出其它策略。main 重导出的参数与核心操作必须是 base 的同一组绑定，不能分别创建参数或 prompt。

依赖方向：main 复用 base；base 可从独立的 merge 实现取得默认 append；标准 merge 不依赖 amb 的控制效应，不形成反向循环。公开模块边界不强迫增加一套内部抽象层或公共 Stream 类型。

严格说，当前 for/amb 并不一定构造向量；无长度迭代目前由惰性 sequence 供应。它归 main 的理由是它属于构造备选的派生语法。因此，将来换成协程供应也不改变公开模块边界。

原生 sequence 到 make-amb 的薄适配（当前的 sequence->amb）可以继续作为实现辅助；是否公开它、是否保留 v2 的 thunk 过程入口 in-amb* / in-amb*/do，可在审核时完善导出表，无需把它们当成新的控制原语。

## 2. 核心语义保持 demo 的方向

```racket
;; Generator = () -> (values Result Generator)
;; Result = list? | #f | exact-nonnegative-integer?
;; Merge = Generator Generator -> Generator
```

列表是一个元素的整组返回值，空列表是零返回值答案；#f 终止后不再调用 next；n 表示 n 个逻辑暂停，0 为无事件推进，不结束、不换边、不调用 handler。生成过程与残余采用 single-pass 所有权约定。

make-amb 在实际执行时捕获后续、读取并固定当前 merger；各分支带着同一后续交给 merger。amb 与循环语法通过供应主体 thunk、再在后续中调用它来派生，不能提前执行主体。

默认 merger 保持 amb-append。v2 的 current-amb-depth-first? 和 current-amb-fair? 不再作为 v3 的策略入口，由 current-amb-merger 统一指定；不假设旧的两个全局前沿参数存在逐项等价的替代。

## 3. 自定义 merger 与代数律

正式版不先把零元律、单备选等式或结合律强制给所有自定义 merger。文档区分协议/所有权要求，与某个策略额外满足的性质。

普通合并策略可建议保留答案、满足空搜索的单位律，并说明暂停与公平性；内置四种给出各自的性质与对照测试。自定义策略可以有不同的行为，库不宣称它自动保留这些等式。

例如，按原始右折叠解释两个备选得到 μ(ka, μ(kb, empty))，化简为 μ(ka,kb) 需要相应右单位律；单备选直接等于执行主体也依赖该条件。没有该律时仍保留原始操作语义，不偷偷删除末尾空选择或按过程身份做 singleton 捷径。

任何依赖单位律、结合律等性质的优化，都要限定到已知满足条件的策略；不能直接作用于任意自定义 merger。四种标准函数的存在不限制使用方定义自己的合并方式。

## 4. 供应阶段的效应与实现选择

正式版方向：供应备选期间，试图影响当前搜索的 amb/make-amb、amb-fail、amb-pause 应明确报错；主体中的效应正常；完整的独立嵌套搜索允许。观察回调影响外围搜索的边界也需在正式异常设计中明确，不能靠迭代器偶然报错定义语义。

这与“用 for/stream 还是协程供应”是两个独立问题。当前 v2 的协程解决了循环体捕获迭代机制的问题，但不会自动给子句效应一个统一的可重放语义。可以提取 v2 的协程供应机制，继续交给 v3 的 make-amb/merger；不搬回 v2 的 frontier 控制层。

审核时比较两种供应实现的惰性、源调用顺序、作用域和实现成本，再决定正式实现；demo 暂时不加入这些阶段检查。没有把子句不受支持误称为所有实现都无法支持：支持它需要另外明确搜索如何影响余下循环。

## 5. 两种观察入口

沿用 v2 的分工：in-amb 返回带缓存的 stream；in-amb/do 返回单遍 sequence。前者重复读取已缓存元素不重跑搜索；后者再次迭代继续共享游标，耗尽后稳定为空。

#:on-pause 保留，默认跳过暂停；每个逻辑暂停一次回调，其零/多返回值自然成为一个观察元素，不送回搜索后续。缓存版缓存最终观察到的元素，包括 handler 的结果，重复读取不重跑 handler。

## 6. 审核与实施顺序

先以 demo.rkt 的简明核心为基准审核，再落实以上模块和异常边界，最后在相应性质保证下优化。正式版的协程供应、缓存 stream、异常检查和模块拆分尚未实现；先前实验的 benchmark 不能当作这些实现的性能结论。

审核重点：make-amb 与派生语法的后续作用域；自然数暂停的事件语义；自定义 merger 不守某些律时的明确行为；单遍/缓存接口；供应效应检查是否误伤主体或嵌套搜索；模块导出与绑定是否保持一致。
